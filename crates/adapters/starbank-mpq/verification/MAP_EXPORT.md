# Offline archive copy qualification

WP-09 evidence for `dfe70d8`. The test used macOS 14.7.2 arm64 on local APFS, Rust 1.100.0, StormLib v9.40 and `stormlib-rs` 0.0.3 with its default features disabled. All archive entries and output paths were synthetic and local. [StormLib v9.40](https://github.com/ladislav-zezula/StormLib/releases/tag/v9.40) · [Rust crate source](https://docs.rs/crate/stormlib-rs/0.0.3/source/)

| Operation | Observed result |
| --- | --- |
| Verify an independent copy | A bounded `read_snapshot` followed by `commit` with `CommitIntent::CreateNew` returned `CommittedVerified`. The destination digest matched the original and a whole-file comparison found identical bytes. Reopening the original produced the same fingerprint. |
| Preserve an unlisted asset | StormLib independently reopened both the original and the created copy without a listfile. The two known-to-the-oracle members, `MapScript.galaxy` and `Assets\Opaque.bin`, returned exact bytes. |
| Refuse a destination collision | Create-new rejected publication to the source path, previous copy, existing regular file, hard-link alias and symbolic-link alias. The test confirmed the existing bytes and symbolic link remained intact. |
| Enforce bounds | Source snapshot and destination commit refused a limit below the fixture length. The refused commit created no output. |
| Evaluate the candidate Rust rewrite | `MpqArchive::add_file_from_bytes` refused a harmless annotation append to a separate synthetic copy with unnamed entries. The existing and original archive bytes remained identical. |
| Evaluate a native reference append | StormLib added a harmless annotation to a different synthetic copy. Its read-only reader verified both original member payloads and the new annotation. The archive bytes changed and the original archive digest remained the same. |

The complete original and verified copy both had SHA-256 `9bddf87cbde5a55a237e2cc9f20cd47086996e29a4025e9cc870c8f1d9c525fd`. The opaque asset had SHA-256 `7f133d491e6fba0043017d1e210a5ee3648a45000ee1515959a3891b6f8f4860`. The comparison covered every byte of the archives' main data streams. Filesystem metadata, ACLs and resource forks on the newly created destination were outside this probe.

For reproduction, build the pinned StormLib source with the [adapter fixture instructions](../tests/fixtures/README.md). Create a V1 archive with 16 file slots, 4,096-byte sectors and listfile creation disabled. Add a plain text script containing `// Name: Synthetic only\n// Author: Archive Fixture\n` and a stored opaque asset containing the byte values 0 through 255 followed by `ff 00`, UTF-8 `opaque fixture`, and `00`. Open the source read-only, use a 1 MiB snapshot and publication bound, and publish to a new absolute path with `CommitIntent::CreateNew`. Check the receipt, compare the whole file with `cmp`, and compare the two named entries with the independent StormLib reader. Use separate temporary copies for the candidate and reference append tests. The test used a canonical scratch path because the native file policy refuses symbolic links in parent paths. [Snapshot and commit contract](../../../platform/starbank-fs/src/lib.rs) · [Create-new publication and verification](../../../platform/starbank-fs/src/native/commit.rs#L45)

The Rust writer's manifest capture requires names for all live entries. The unnamed-entry refusal observed here agrees with the pinned source. StormLib's successful append verifies one ordinary write on an authored V1 fixture. That result leaves real SC2 archive variants, archive repair semantics, broader member retention under rewrite, and Windows native publication unverified. The repair capability remains unavailable. An explicitly authorized exact-copy export can preserve archive bytes where the native create-new storage capability is available. [Pinned Rust writer source](https://github.com/notOrrytrout/stormlib-rs/blob/f81ba70fac3025701a3ff4a868f43192ac71bb0b/src/file/add.rs#L197-L235) · [Windows storage capability](../../../platform/starbank-fs/src/unsupported.rs#L31)

## Upstream action and writer cross-check

The pinned StarBank v2.0 action uses member presence as a heuristic. It fills missing entries with fixed bundled data. The bundled trigger XML contains zero child records. The external Tools action changes the chosen archive directly, and the map export action can apply the same change to its copy. The native wrapper discards the return values from entry creation, writing and finalization. Its bundled DLL is a 32-bit Windows x86 binary. These behaviors establish the scope of upstream parity and the limits of its verification. [Pinned action](https://github.com/BlueRaja/Starbank/blob/1f95ab3425753b12d6387d327870dc6d408c49ac/StarBank/MapProtection.cs#L21-L48) · [External Tools flow](https://github.com/BlueRaja/Starbank/blob/1f95ab3425753b12d6387d327870dc6d408c49ac/StarBank/MainForm.cs#L293-L318) · [Copy flow](https://github.com/BlueRaja/Starbank/blob/1f95ab3425753b12d6387d327870dc6d408c49ac/StarBank/MainForm.cs#L220-L249) · [Pinned native wrapper](https://github.com/BlueRaja/Starbank/blob/1f95ab3425753b12d6387d327870dc6d408c49ac/StarBank/StormLibWrapper.cs#L109-L120)

The independent writer probe used the current reader at `c8d0b0f`, official Rust 1.100.0, macOS arm64, StormLib v9.40 and `wow-mpq` 0.7.0 with default features disabled. The synthetic archives used MPQ V1, V2 and V4, zero archive offsets and no listfiles. Each contained a stored text member and an unlisted, multi-sector bzip2 binary member. Each writer operated on a separate copy and added one generic, locally authored text annotation. [StormLib release](https://github.com/ladislav-zezula/StormLib/releases/tag/v9.40) · [Pinned Rust candidate](https://github.com/wowemulation-dev/warcraft-rs/blob/627b3a0d99b8420cc7640b5f99aff18c878e1529/file-formats/archives/wow-mpq/src/modification.rs)

| Writer and format | Observed result |
| --- | --- |
| StormLib V1, V2, V4 | All three copies reopened in StormLib and both original payloads and the annotation matched exactly. Both retained members kept their original offsets, packed sizes, flags and raw packed bytes. The production StarBank reader extracted the original metadata bytes from each copy. |
| `wow-mpq` V1 and V2 | The candidate returned success from flush. Its own reader and StormLib recovered all three member payloads. The production StarBank reader rejected both outputs because each updated classic block table extends beyond the header's declared archive length. |
| `wow-mpq` V4 | The candidate returned success from flush. Its own reader and StormLib rejected the copy on reopen. The declared archive size remained 3,576 bytes while the new hash table began at offset 3,867. The production StarBank reader rejected the stale classic table size declaration. |

Every original archive retained its before-test SHA-256 digest. The retained bzip2 member had 2,099 packed bytes and the same packed SHA-256 `cadd6fe5d403d066fc0bac1891700d581433ea0f5f546ad6488ef516ee513a16` in each original and StormLib-written copy. The Rust writer source explains the stale headers. It publishes new table locations while serializing the old archive length, and its V4 update leaves the classic table byte-count fields unchanged. [Pinned writer header update](https://github.com/wowemulation-dev/warcraft-rs/blob/627b3a0d99b8420cc7640b5f99aff18c878e1529/file-formats/archives/wow-mpq/src/modification.rs#L1580-L1645)

This qualifies one ordinary native append and raw member preservation on these fixtures. Offline restoration of an authored map still requires the owner's original missing components, verified output from a qualified native backend and target editor acceptance. The synthetic probes used only generic archive members. The existing unavailable capability remains appropriate while those requirements are open.

The opt-in native adapter now pairs bounded V1 append with an independent preservation verifier. [Native append qualification](../../starbank-mpq-stormlib/verification/NATIVE_APPEND.md) records the synthetic proof and remaining release and editor checks.
