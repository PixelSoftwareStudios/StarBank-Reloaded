# Safe save, permissions, backups and recovery

Safety invariant: original file must not be truncated or partially written on failed save; no silent data loss, metadata change or race. Distinguish atomic replacement, durability across crash/power loss, verification and recovery. No universal atomicity claim across all filesystems, network shares, Windows locks or OS failures.

## Save contract

Default primary Save overwrites selected bank. Save dropdown exact labels `Save (Overwrite)`, `Save As…`, `Save w/ Backup`, separator, `Copy bank XML to clipboard`. Re-sign default on via Quick Options. Dedicated selected-bank Re-sign and external re-sign also use prepare/commit. Export/copy are valid with game absent. All paths:

1. Capture revision, flush/validate input drafts and context; resolve destination signing name/handles *before* computing signature. Detect external change via open identity and content digest (SHA-256 or BLAKE3 candidate for integrity, SHA-1 only for SC2). Reject missing or unreadable target as appropriate. Never infer authority from display name.
2. Prepare exact serialization in memory or bounded streaming; apply optional signing to a transaction-local copy; reparse and verify semantics/signature. No side effects on failure. Auto-sign off preserves old signature with stale/invalid diagnostic and explicit confirmation where necessary.
3. Authorize destination; check regular file and symlink/reparse policy; explicit overwrite decision; no surprise follow-through. If required backup, create unique verified copy of **current on-disk target bytes**, not stale original cache. Backup failure aborts write.
4. Commit through native storage service: same-directory temporary file, exclusive creation, write-all, preserve supported permissions/security metadata before replace, flush, close, re-check expected identity/fingerprint under best available synchronization, native replace, parent sync where meaningful/supported, read back/verify. Serialize commits per target, no blind retry, document remaining TOCTOU limitations where external writers ignore locks. If exact metadata cannot be preserved under policy, fail safely or explicit user-approved alternative Save As, never silently ignore errors. Handle hard links, symlinks, readonly ACL/owner, extended attributes, timestamps as applicable. No automatic elevated permissions or chmod target to force write.
5. Report `CommittedVerified`, `RejectedUnchanged`, `RolledBackVerified`, `CommitUncertain` (or equivalent typed outcomes). Verification failure after replacement is not simple retryable error; preserve evidence/temp/backup and offer explicit recovery; do not overwrite unknown state. Update path/baseline/dirty only on verified success; progress and cancellation safe boundaries. Reset is memory-only.

## Cross-platform writer evaluation

Prefer maintained [atomic-write-file](https://github.com/andreacorbellini/rust-atomic-write-file) or equivalent that documents native Windows and Unix semantics. Spike before adoption: actual source/version/license, creation vs replacement, metadata policy, open handles, sharing violations, ACLs, alternate streams, extended attributes, filesystem-specific guarantees, sync and fault injection. Previous Go library recommendations (`natefinch/atomic`, nonexistent `creachadair/renameio`, nonexistent `itchio/wharf/renameio`, `google/renameio` which explicitly lacks Windows support) are **not** approved. Old Go `os.Rename` and ignored chmod error insufficient. Direct `os.WriteFile` on existing file would retain normal mode bits but is non-atomic; do not sacrifice safety for simplicity. Do not invent API or maintenance status. Rust library may preserve Unix permissions while not preserving Windows ACL/ownership; verify and isolate remaining native metadata operations. Prefer library over maintaining raw Win32 calls; if gaps require native adapter, explicit ADR and tests. No unsupported `REPLACEFILE_WRITE_THROUGH` guarantee. Handle AV/sync locks without destructive fallback, provide clear errors. On browser, user-authorized File System Access API write/close where supported, no claim of native durability; downloads are safe-copy default and fallback. Do not overwrite browser file without handle/permission and explicit intent.

## Backup parity + improvements

- User's explicit Save w/ Backup naming: `bankname_YYYYMMDD_HHMMSS.sc2bank.bak` (retain basename, portable timestamp; avoid collisions via suffix/exclusive creation; timezone display and UTC catalog). For desktop same folder for explicit Save w/ Backup; managed automatic backup catalog in OS app data by default with configurable location. No version overwritten. Do not count `.bak` as live bank. Preserve bytes and metadata as feasible, hash/length/identity, backup creation time, source, context, reason. No retention deletion without policy and user approval. Mark missing/unverified backups distinctly.
- StarBank 2.0 parity: backup once before first overwrite of bank per session by default, back up selected map's banks, Tools “Back up all bank files”, restore selected bank from list, status/never-backed-up indicator in map list, back up current target before restore so operation reversible. Explicit backup always creates one even after automatic policy triggered. Auto-backup policy customizable (first-per-session/every overwrite/off with warning); no hidden backup removal. Save overwrite vs Backup option remains meaningful. Use same commit/recovery pipeline for restore; verify backup digest and original identity, show diff/confirmation. Do not restore into unexpected context silently; restore exact bytes by default rather than auto-re-signing saved snapshot. Offer Save As/export of backup. Web backup downloads or session/local user-authorized backup catalog only with clear limitations; no promise of automatic local backup with unsupported browser APIs.
- Bulk backups bounded, per-file reports and aggregate result, no all-or-nothing claim across files; cancellation before each file, no destructive rollback of successful backups. Map index records backup status without loading every bank. Never use actual user's bank data in logs/CI.

## Evidence obligations

Failure injection at temp creation, write (short write/out of space), metadata, sync, backup, conflict check, replace, verification, crash and restart. No originals destroyed when precommit fails. Recovery journal/minimal outcome record only as needed; retain uncertain artifacts. Test no permission/ACL escalation, read-only, Windows sharing lock, destination same/different filesystem, symlink and hardlink policy, SaveAs name/context, concurrent edits, file modified during save, browser denial/download fallback. Real Windows/macOS tests mandatory before safety claim; POSIX tests alone insufficient. Cache/settings writes use same safety policy appropriate to non-bank data.
