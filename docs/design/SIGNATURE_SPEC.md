# SC2 bank signature compatibility

Use independent format expectations, authorized SC2-generated banks and observed game behavior to qualify compatibility. [Historical source consultation](../verification/VERIFICATION_REGISTER.md#historical-evidence)

## Required behavior

Signing context is author handle, player handle and bank basename without extension (all exact strings). Example handles `1-S2-1-1234567`. No raw XML hash, null-delimited stream, map name salt, RSA or secret key. Signature uses SHA-1 for legacy compatibility only, not security or backup integrity. Canonical sequence is the three context strings followed by sections in ascending stable ordinal name order. Within each section: section name, each distinct key occurrence/group in ascending stable ordinal key name order, followed by named value children in ascending stable ordinal child name order. For each value child include its name and type attribute name and lexical attribute value, except `text` content is omitted. Empty keys contribute their key name, not a fabricated Value. No delimiter is added. Signature itself and version are not included. Output uppercase hexadecimal (40 chars).

- Ordinal means UTF-16 code-unit comparison as in `StringComparer.Ordinal`, not locale collation, lowercase or human natural sort. UTF-8 string comparisons agree for ASCII, but can differ for supplementary Unicode. Test e.g. U+10000 vs U+E000. Preserve stable equal-key order without mutating source. Rust stable sort on borrowed references/indices; no lazy generator requirement. Never make debug `Display` formatting the signature key.
- ASCII conversion maps each ASCII UTF-16 code unit to its byte and each non-ASCII code unit to a replacement byte. Test supplementary characters with independently calculated bytes and authorized SC2 fixtures. XML rejects malformed surrogate references. Reject inputs whose canonical representation is uncertain. Keep valid content and apply neither case folding nor Unicode normalization.
- Validate all signing context fields. Infer from known path and account information, or prompt for author/player/bank name for external files and ambiguous legacy locations. Preserve handles case/lexical form; distinguish account numeric directory from player handle. Use optional context on inspection. Do not report a valid signature without verified context. Status: unsigned, valid, invalid, unsupported, missing context, malformed; distinguish unverified from invalid. Verification compares stored digest to recomputed result without mutating document.
- Save As must establish destination signing context **before** signature computation: canonical destination may imply new bank name/player/author; external export must ask or retain explicit intended game context, not infer from arbitrary export name silently. Copy XML is the same prepared export with no filesystem write; if auto re-sign disabled preserve signature or warn if stale. Explicit Re-sign always signs after context validation. If disabled auto-sign and edited data invalidates stored signature, warn and allow explicit informed export, never call it verified.
- Preserve each key occurrence and its named children, including children without a type attribute. Check repeated keys and empty children with independent fixture expectations. Reject malformed inputs with unspecified behavior. Verify the prepared output after serialization and reparse. Custom map validation remains outside standard bank signing compatibility.

## Test obligations

Test known ASCII SHA-1 digests, independently assembled synthetic byte streams, and signatures from documented authorized SC2 captures with multi-value and text fields. Cover locale independence, stable ties, UTF-16 ordering, ASCII fallback, empty keys, unchanged source order and lexemes, absent and mismatched signatures, and changes to the bank name or context. Compare native, WASM and CLI results. Verify edited copies in an authorized offline game run before claiming in-game acceptance.
